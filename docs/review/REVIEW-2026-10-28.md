# ultraroute: an independent review

Read-only review of the repository at commit `184f640` (main, 2026-10-28). Nothing was changed. Line
numbers are from that commit. Every claim below was read in the code or measured in the lab data
under `~/Software/ultraroute-lab`; where I could not verify something I say so.

How to read a finding: each one says **where** (file:line), **confidence** (high / medium / low),
**effort** to fix (hours / days / weeks), and whether it is **definitely wrong** (a bug, a false claim,
or a goal the code cannot meet as written) or a **judgment call** (a design choice I would make
differently).

Scope: the MIT core under `core/crates` (kicad-pcb, board, grid, topo, morph, ultraroute, web), the
tools under `tools/`, the benchmark data, and the studio only where it runs the router.
`copperroute/`, `copperroute-main/` and `freerouting/` are separate GPL projects and were not reviewed.

---

## Executive summary

The core is a real router. Written in six days by agents (100 commits, 96 of them co-authored, 28k
lines of Rust), it routes bare PCBench boards and is judged by KiCad's own DRC after a zone refill: on
the full 1,182-board corpus at 120 s on one thread it leaves 925 boards clean (78.3%) against
FreeRouting's published 857 (72.5%). The two target boards route completely. The board model is
pinned to KiCad 9's DRC by tests, geometry is integer nanometres, every piece of copper is checked
exactly before it is kept, and the data structures are careful about determinism. That is a strong
foundation and I would not throw it away.

It is not yet the router the brief asks for ("throw any board at it and have it complete, fast,
without pegging the machine"), and the reasons are structural rather than tuning. Ranked by impact:

1. **Time and memory are not bounded, and `--timeout` is advisory.** Each stage gets a wall-clock
   slice of the timeout, several stages (pre-fanout, plane joining, the diff-pair search's inner
   loops, negotiation's set-up) have no budget at all, and the A* search has no expansion limit, so an
   unreachable target explores the whole grid. In the full PCBench run 166 of 1,182 boards hit the
   120 s limit, 157 of the 257 failures are time-limited, and individual boards ran 351 s, 368 s
   and 421 s against a 120 s timeout; one hung past 660 s. Re-run today with `--timeout 60`: a
   2,000-net two-layer board took 194 s (162 s of it silent, before negotiation's first round), and
   an 80 × 50 mm board with 46 footprints spent 221 s coupling its first differential pair, 312 s on
   all four, and was still running when killed at 400 s with no output file written. Memory scales
   with board area ÷ cell² × layers × (threads + classes) with no cap or coarsening: a 10 µm run
   peaked at 5 GB. See §3.2, §3.6, §A.4.
   *Definitely wrong; high confidence; days to make hard, weeks to make graceful.*

2. **Results are not reproducible, and the benchmark cannot see changes smaller than ±5%.** Every
   stage's budget is wall-clock, so the output depends on machine load; the via-reduction pass has a
   flat 8 s cap; negotiation runs Gauss-Seidel on one thread and Jacobi on more, so the thread count
   changes the algorithm; and the benchmark runs at one thread while the CLI defaults to half the
   cores. Five PCBench runs of the same clean binary, recipe and seed on the same 100 boards disagree
   on "clean" for 1–7 boards per pair and on via count for 38–48 boards. Most of the per-board
   via-count comparisons in the lab notes are therefore noise. See §1.7, §2.3.
   *Definitely wrong for a benchmark-driven process; high confidence; days.*

3. **The pipeline driver is agent sprawl, and the good router is not the default.** `run_with_solver`
   is one 1,035-line function with about twenty inline stages, 77 command-line flags, hand-split time
   fractions, and ten written-down "default" recipes that disagree (the CLI with no flags routes one
   connection at a time and nothing else; the studio, `tools/lab.py`, `tools/pcbench.py`,
   `tools/search.py`, two READMEs, the library guide, the film recorder and three job READMEs each
   say something different). Six plough variants, two topological-routing modes,
   `--escape`, `--clear-lanes`, `--push`, `--chase`, `--first*`, `--restart` and `--negotiate-legacy`
   remain in the main path although the logs record them as tried and abandoned. See §1.3, §1.5.
   *Judgment call on structure, definitely wrong on defaults; high confidence; days.*

4. **There is no regression gate.** CI builds the website and runs no tests. 210 tests exist and
   nothing runs them automatically. The benchmark harness records results but never compares two runs
   or fails on a regression; runs are keyed by commit without a binary hash; the published baseline
   was taken from a dirty tree; a referee failure is scored as a router failure. See §2.3, §2.4.
   *Definitely wrong; high confidence; a day for the gate, more for a noise-aware comparison.*

5. **The algorithm has no global stage, and the GPU is solving the wrong problem.** Everything happens
   on one uniform 50 µm grid: negotiation, finishing, rip-up, ploughing. That is why memory and time
   scale with board area, why fine-pitch escapes needed a separate 10 µm sub-router, and why via
   counts run 2–5× FreeRouting's (layer choice is made per net, greedily, with per-stage via prices
   that differ by stage and by whether the board has planes). The GPU path computes a full-board
   Bellman-Ford field per connection, which is O(nodes × path length) against the CPU A*'s
   O(patch), so it is 10× slower, as the roadmap already records; the browser build does not use it
   at all. The right next step is a coarse global routing and layer-assignment stage feeding the
   existing detailed router through the `--regions` mechanism that already exists. See §3.
   *Judgment call; high confidence on the diagnosis, medium on the remedy's payoff; weeks.*

What I would **not** do: rewrite the board model, the exact checker, the KiCad reader/writer or the
search primitives. They are the parts that work. What I would **stop** doing: adding stages and flags
to recover the last open connection on one board before the budget, determinism and gate problems are
fixed, because those problems make every such experiment unmeasurable.

## 1. Code quality and architecture

### 1.1 What is good

- **Integer geometry with exact checks.** `board::geom` keeps coordinates in `i64` nanometres and uses
  `i128` cross products for segment intersection (`core/crates/board/src/geom.rs:183-197`);
  distances are `f64`, which is exact for every board-sized integer. The checker applies KiCad's
  0.5 µm epsilon (`check.rs:10`). Nothing in the core uses `f32`.
- **Every piece checked before it is kept.** `grid::route::lay` inserts each track and via and runs
  the exact checker, discarding the lot on any violation (`grid/src/route.rs:524-558`). The grid is
  conservative by construction (`grid/src/grid.rs:1-5`): it may refuse a legal path, never accept an
  illegal one. This is the reason "0 new errors by KiCad" is routine.
- **The board model is pinned to KiCad.** `board/tests/kicad_agreement.rs` compares open-connection
  and clearance counts with `kicad-cli` on both real boards in four variants, exactly except a
  documented 3-item connectivity gap. `kicad5.rs` and `mask.rs` encode the rules the PCBench errors
  taught (slots as edge, mask openings, drill offsets).
- **Determinism was designed in.** Ordered containers where order reaches the output (`BTreeSet` for
  given-up pairs, sorted `near()` results, `BTreeMap` for terminals, `commit_order` with explicit
  tie-breaks at `negotiate.rs:885-895`); Jacobi rounds write each path into its own slot
  (`negotiate.rs:1420, 1448`); `HashMap` iteration is used only where the operation is commutative.
  Neither I nor the two audits that looked found a hash-order dependence that reaches the written
  board (two reach the live stream and `--auto-planes` tie-breaks; §1.7).
- **Lint-clean.** `cargo clippy --workspace --all-targets` at this commit gives 25 warnings, all
  cosmetic (complex types, `is_multiple_of`), none dead-code. No `TODO`, `FIXME`, `#[allow]` or
  `unsafe` outside one byte-cast in the GPU path.
- **Good library documentation.** `docs/library.md` is an accurate, readable description of the
  crates, units, frames, soft copper and spans; its stage list and `core/README.md` are incomplete
  rather than wrong (§1.5). (The repository's root `README.md` still describes copperroute as "the
  router"; §1.5.)

### 1.2 Module boundaries and ownership of the board and rules

The layering is right and is respected: `kicad-pcb` (text ↔ records, metres) → `board` (nanometre
model, index, connectivity, checks) → `grid`/`topo`/`morph` (algorithms) → `ultraroute` (pipeline)
→ `web`/studio. `board` is the single source of truth while routing; the file text is kept beside it
and edited by span. That design is sound and I would keep it.

Where the representation is copied or thinned:

- **Rules live in three places.** `kicad_pcb::Rules` (metres, per class and per `.kicad_dru`
  select), `Board::net_clearances` (per-net nanometre maximum, `board/src/model.rs:300-302,
  343-347`), and `grid::Profile` (per-net sizes recomputed from `Rules` on every call,
  `grid/src/grid.rs:46-68`). `Profile::for_net` is called per connection per stage and does string
  matching on class names each time. Not wrong, but the third copy is where the via-size rule
  (`min_via_annular_width`, `:64-65`) lives and the checker does not check annular rings at all,
  so a via that `Profile` fails to grow is caught only by KiCad. *Judgment call; medium; days to
  unify.*
- **Holes are circles.** A pad's hole is modelled as a circle of the drill's smaller diameter
  (`model.rs:411`). An unplated slot gets a keepout capsule along its length (`:486-502`), a plated
  slot does not: its hole-to-hole and hole-to-copper clearances are checked against a circle, so a
  track or via near the ends of a plated slot can pass the router's check and fail KiCad's. The
  roadmap lists "holes as slots" as open. *Definitely wrong (a known gap); high confidence; a day.*
- **Zones without fills are invisible.** Pours are built from `(filled_polygon ...)` records
  (`model.rs:578-590`). A zone that has never been filled (common in boards saved before a refill)
  contributes nothing, so a kept block pour or a plane layer with no fill in the file is not an
  obstacle. For refilled pours this is harmless by design; for `kept: true` pours and `--planes`
  it is a silent hole. *Judgment call; medium; a day (fill the zone outline, or warn).*
- **Via layer sets.** A via's layers are the index range between its two named layers
  (`model.rs:540-544`); the writer emits only plain `(via ...)` records (`kicad-pcb/src/write.rs:89-101`),
  so blind, buried and micro vias can be read but not produced, and `Rules.allow_blind_buried_vias`
  / `allow_microvias` are read and consumed nowhere. Fine for the target boards, but it should be
  stated as a limit rather than left implicit. *Judgment call; high; days to add.*
- **Pads with several polygons** become one `Kind::Pad` item per polygon with the same footprint and
  number (`model.rs:454-461`), and `same_pad` makes the checker ignore them pairwise. Connectivity
  anchors at the centroid of the first polygon only (`connect.rs:427-430`), which can miss a join to
  a custom pad whose anchor polygon is small. *Judgment; low-medium confidence; hours.*
- **Layers** are a bitmask in `board`, names in `kicad-pcb`, and routing-layer indices (a
  `Vec<usize>` of board layers) in `grid`; conversions are explicit and local. Fine.

The spatial index is a `HashMap<(layer, cell), Vec<ItemId>>` with 1 mm cells (`model.rs:12, 309`).
Every `near()` sorts and dedups a fresh `Vec` (`:768-792`), and `remove()` does a `retain` per cell
(`:753-764`). `check_item`, `joined`, `dangles` and `terminals` call `near()` thousands of times per
connection. A flat `Vec<Vec<ItemId>>` grid indexed by (layer, x, y) with a reusable scratch buffer
would remove the hashing and the allocation; `Board::clone` (used as the undo mechanism by rip-up,
nudge, shove, the rescue and the restart loop) clones the whole map each time. *Judgment call; high
confidence that it is a cost, medium that it is a significant one; days.*

### 1.3 The pipeline driver

`core/crates/ultraroute/src/lib.rs` is 2,433 lines: a 165-line `Args` struct, a 300-line hand-written
flag parser, the `Live` frame writer, and `run_with_solver` at lines 1191–2226. The function:

- runs about twenty stages inline, each with its own `eprintln!` summary that `tools/lab.py:91-98`
  then parses back with regular expressions;
- shares out `--timeout` by fractions chosen per stage: pairs get a quarter (`:1440`), topo 0.4
  (`:1550`), topo-first 0.25 (`:1576`), first-negotiate 0.25 then 0.15 (`:1605, :1638`), negotiation
  half (`:1699`), restarts 0.7 or 0.8 of the whole (`:1515-1519`), the plough 0.65 of what is left
  when rubber bands follow (`:2001-2007`), nudging what is left minus `--shove-seconds` (`:2089`);
  pre-fanout (`:1374-1390`), plane joining (`:1422`), via reduction (its own 8 s, §1.7), cleanup and
  length matching get no share;
- carries three parallel lists of copper (`laid`, `fanout_laid`, `pair_laid`) with hand-maintained
  rules about which stage may rip which (`:1355-1357, 1413-1417, 1749-1752, 1810-1812, 2152-2161,
  2186-2193`), ending with a dedup "because escapes may have joined `laid` twice over";
- snapshots the whole board to undo a stage (`:1856, :1914`) and keeps a best-of across restarts
  (`:1966`).

There is no `Stage` abstraction, no single deadline object, no structured stats. Each new idea has
been added as another `if a.flag { ... }` block with its own time slice. This is the single biggest
source of fragility: the time-budget arithmetic is wrong in at least two places today (§3.6), and the
interactions between stages (what is soft, what is locked, what is pruned when) are only in the
author's head and `docs/library.md`.

*Judgment call; high confidence; 3–5 days to refactor into stages with one budget and one stats
schema, without changing behaviour.*

### 1.4 CPU/GPU split and precision

**Precision.** The CPU and GPU agree by design: costs are `u32` (10 per straight step, 14 diagonal,
`via_cost` per layer change, `search.rs:9-11`), the WGSL kernel uses the same integers and
`atomicMin` (`relax.wgsl:35-52`), and the walk-back uses the same neighbour order (`relax.wgsl:130-157`
vs `search.rs:111-122`). No `f32` anywhere. The GPU field is bit-identical to the CPU field when it
converges, and there is a CPU test that A* paths cost the same as the full field on 59 random grids
(`search.rs:568-581`). This part is right.

**What the GPU does.** `GpuSolver::run_relax` (`gpu.rs:350-470`) uploads the whole blocked / penalty /
via / cost buffers for a batch of up to 16 fields (`:437-441`), then dispatches the `relax` kernel 32
times per submission and reads back a changed flag (`:452-469`). Each dispatch launches one thread per
node of every field (`relax.wgsl:55-60`) and returns at once unless the node's frontier bit is set.
That is Bellman-Ford with a dense frontier scan: work per connection is O(nodes × rounds), and rounds
grow with path length in cells. The CPU `route_astar` touches a patch around the connection. On the
earring's 3.5M-node fields the roadmap measured ~110 s per negotiation round on the GPU against
~10 s on CPU threads, and that is the expected ratio for this algorithm, not a tuning problem.

The GPU audit's estimate of the traffic, consistent with the code: for the earring's 3.5M-node fields
and the batch of 16, the device buffers are about 730 MB (`blocked`, `cost`, `penalty` at 224 MB
each, `via_blocked` 56 MB), mirrored by host scratch vectors of the same size, plus a fresh 224 MB
staging buffer per `solve_batch` (`gpu.rs:79-84, 483`); every batch uploads the lot (~730 MB), so a
250-connection round uploads about 12 GB; each dispatch launches 56M threads of which nearly all do one
atomic load and exit, and a board a thousand cells across needs one to three thousand dispatches per
batch. With `--gpu`, every stage uses the solver, so `route_open`, rip-up and the plough each pay a
full upload and dense relaxation per single connection (`route.rs:226` → `gpu.rs:284-286`), which is
the roadmap's "58 s vs 22 s CPU".

Correctness notes on the GPU path, from the audit and checked where marked:

- **Deadline and cancel are not checked inside a GPU batch** (`gpu.rs:452-469`), nor inside a
  parallel or batched CPU round (`negotiate.rs:1312-1477`); overshoot is a round: seconds on the CPU,
  minutes on the GPU. The studio server sends `stop` 20 s after the limit and SIGKILLs 8 s later
  (`studio/server/src/main.rs`, per the audit), and the CLI writes its board only after `run` returns
  (`main.rs:54-58`, checked), so a GPU run from the studio can end with no output file. *W; a day.*
- **A failed read-back is swallowed** (`get_mapped_range` errors become empty vectors,
  `gpu.rs:91-94, 259-266`, checked), after which `solve` panics on `remove(0)` of an empty result
  (`:277`) or `route_batch` indexes out of range (`:521`). *W; half a day.*
- **Possible `u32` overflow in late rounds** (unverified): the searches add `c + step + penalty`
  without saturation (`search.rs:68, 317, 331`; `relax.wgsl:40, 90, 96`), while the present price
  grows 1.6× per round and `price()` saturates at `u32::MAX`; a long route through heavily
  contested cells in a late round can wrap to a cheap value. *Medium; hours with `saturating_add`.*
- **A relaxed-atomics hazard in the kernel** (unverified, low-medium): `relax` clears a node's active
  bit then loads its cost; `offer` does `atomicMin` on the cost then sets the bit (`relax.wgsl:44-46,
  66-67`). On different addresses with relaxed ordering an improvement can be observed as
  cleared-and-missed, the field reports converged while inexact, and the trace's exact-equality walk
  then returns `None`: the connection counts as unroutable for that round.
- **GPU routes differ from CPU routes on ties** even where the fields agree, because `CpuSolver::route`
  is A*, whose walk-back sees only touched nodes (`search.rs:344-376`); the equivalence test asserts
  cost only (`search.rs:569-581`).

The GPU path is also **not what runs anywhere that matters**: the CLI defaults to CPU, the benchmark
runs CPU, the studio runs CPU, and the browser build compiles `grid` without the `gpu` feature
(`core/crates/web/Cargo.toml`, `ultraroute` with `default-features = false`), negotiating instead on
a pool of WASM workers that each run the CPU A* (`web/src/lib.rs:179-350, 639-640`). The browser does
carry a verbatim JavaScript copy of `relax.wgsl` (`studio/web/src/lib/router-subworker.js:23-199`,
checked) with its own WebGPU device setup, reachable only if a user types `--gpu` into the studio's
argument box; by the audit's reading its batch notifies one waiter on a shared epoch word and wakes
the wrong sub-worker whenever the pool has more than one, so it hangs on its first batch
(`router-worker.js:124`, `router-subworker.js:550-552`; not executed). There is no working WebGPU
routing today. A second native GPU solver, `GpuSweepSolver` (`sweep.rs`, GAMER-style line sweeps),
is re-exported from `grid/src/lib.rs:49` and used by nothing: dead code (228 lines + 127 of WGSL),
single-field, per-call-allocating, untargeted. `search::pocket_bbox` (`search.rs:392-479`) likewise
has no callers, and `GpuSolver::pocket_trapped` (`gpu.rs:298-348`) duplicates the pocket check in
`route_astar` (`search.rs:229-281`).

The `--regions` costs and the two-layer directional costs are CPU-only (`route.rs:169`,
`negotiate.rs:619`, `grid.rs:775`, `relax.wgsl:83`; the browser pool likewise builds grids with no
`region_cost`, `web/src/lib.rs:458, 513`), so the GPU solver and the browser silently route a
different problem from the native CPU on two-layer boards and on boards with regions. The audit also
notes `required_limits: adapter.limits()` (`gpu.rs:65`): the native card's limits are requested, with
no chunking, so a 224 MB storage binding is assumed.

*Verdict: definitely the wrong GPU algorithm for detailed routing (high confidence); the "GPU
accelerated" and "WebGPU" claims in the design doc and README are not met today (definitely wrong as
documentation). What to do with it is in §3.4.*

**Threads.** The CPU path uses `std::thread::scope` with one `RouteGrid` per worker and an atomic
job counter (`negotiate.rs:1416-1452`) only inside negotiation rounds; everything else is single
threaded. The default thread count is half the cores (`lib.rs:1491-1492`). Per-worker memory is one
grid view (about 9 bytes per node) plus the thread-local A* buffers, five `u32` per node
(`search.rs:150-158, 176-182`): on a 3.5M-node board about 100 MB per thread, on a 200 × 150 mm
six-layer board at 50 µm (72M nodes) about 2 GB per thread. Nothing adapts the cell to the board.

### 1.7 Determinism and reproducibility

The data structures are deterministic (§1.1), the search is deterministic, and the seed machinery
(`jitter.rs`) is deterministic. The *process* is not, for three reasons, all definite:

1. **Wall-clock budgets inside the algorithm.** Every stage's `max_seconds` is checked per connection
   or per try, so under load a stage does fewer tries and the copper differs. The via-reduction pass
   has a flat default of 8 s and 3 passes (`vias.rs:54-55`) that the CLI never overrides
   (`lib.rs:2122-2128`); on the locked earring that pass alone made the via count 375 on a quiet
   machine and 466 under load (measured earlier today). `prefanout::probe_trapped_nets` hardcodes
   4 threads and 4 s + 2 s (`prefanout.rs:280-281, 294`); the topo crate hardcodes 3 s and 2.5 s
   (`topo/src/lib.rs:320, 346`); rip-up's reroute is 10 s per attempt, nudge's 5 s, the plough's 20 s
   and 10 s (`ripup.rs:43`, `nudge.rs:50`, `shove.rs:94-95`).
2. **Thread count selects the algorithm.** `threads == 1` negotiates Gauss-Seidel (each connection
   sees the routes before it in the same round), `threads > 1` Jacobi (all see the previous round)
   (`negotiate.rs:679-722`). The CLI default is half the cores; the benchmark uses one
   (`tools/pcbench.py:169`); the lab uses four (`tools/lab.py:286`); the browser always Jacobi. So the
   benchmark measures a different router from the one the studio and the CLI run. The test
   `negotiation_is_the_same_on_one_thread_per_round_however_many_run` (`grid/tests/route.rs:113-127`)
   checks 2 vs 4 threads on four summary numbers, not 1 vs 2 and not the copper.
3. **Fresh UUIDs on every write** (`write.rs:114-132`, seeded from `RandomState`), so two identical
   runs never produce identical files; every comparison has to strip them. Two smaller hash-order
   leaks: the live stream's `del` list is built from `HashMap::keys` (`lib.rs:702`), so recordings
   differ byte for byte between identical runs, and `--auto-planes` breaks a tie between two nets'
   pour areas by hash order (`model.rs:658`).

Measured effect (my check, same data the tests audit found): five `pcbench.py` runs of commit
`8c691ec`, clean tree, same recipe, `--seed 0 --threads 1 --timeout 120`, 100 boards
(`pairs1-main` … `pairs1-main5`):

| pair of runs | boards whose "clean" verdict differs | boards whose via count differs |
|---|---|---|
| min over the 10 pairs | 1 | 38 |
| max over the 10 pairs | 7 | 48 |

A 100-board sample therefore cannot resolve a change of fewer than about five boards, and per-board
via counts are mostly noise. The 240-board comparisons I ran earlier today (−8.5% vias with
"190 clean vs 190") are inside this noise on the success axis and only just outside it on vias.

*Fix (days): one `Deadline` object passed to every stage; budgets expressed in work (A* expansions,
negotiation rounds, tries) with the wall clock only as a hard stop; one negotiation mode (Jacobi, the
one users get) or an explicit `--mode`; a deterministic UUID stream behind a flag for tests; and a
test that routes the earring twice and diffs the output.*

### 1.8 The I/O layer (reader, writer, rules)

- The reader is the project's own S-expression parser (`kicad-pcb/src/sexpr.rs`) with the copper
  reader (`copper.rs`) and outline chaining (`outline.rs`); KiCad 6–10 formats parse, KiCad 5
  needs a pcbnew round-trip first (`tools/pcbench.py:98-117`). Arcs become chords at KiCad's 5 µm
  chord error (`model.rs:13-30, 891-908`).
- The writer is a byte-splice: removed spans are cut (taking their line when alone on it),
  replacements inserted, new copper appended before the final paren (`write.rs:37-104`). It cannot
  write arcs, `locked` flags, blind/buried vias or group membership. A locked arc that one stage
  ripped is rewritten as unlocked straight chords (`route.rs:636-645` + `model.rs:525-538`).
  *Definitely a fidelity loss; high confidence; a day for `locked`, more for arcs.*
- `Rules::read` understands the `.kicad_pro` fields in `rules.rs:15-41` and five `.kicad_dru`
  constraint forms; every other custom rule lands in `warnings` and is printed by the CLI, which is

### 2.3 Is the benchmark a regression signal?

It is a good **measurement** and a poor **signal**.

Good: `tools/pcbench.py` routes 1,182 real boards from bare pads under a memory cap, judges them with
KiCad after a refill, counts only violations that involve routed copper, diffs error types against the
bare board, records wirelength, vias, seconds and the commit, and compares with the published
FreeRouting / PcbRouter / RL-MCTS numbers. The lab (`tools/lab.py`) keeps every experiment with
per-stage stats, peak memory and the DRC report, served locally. This is far better than most
routing projects have.

Why it cannot gate a change today:

1. **No comparison.** `report` prints each run alone (`pcbench.py:248-292`); nothing diffs run A
   against run B per board or exits non-zero. Comparisons are done by eye or by ad-hoc scripts (I
   wrote one myself this morning).
2. **Noise floor unmeasured until now** (§1.7): ±5 boards per 100 on "clean", via counts noisy on
   ~45% of boards. The lab notes compare single seeds across arms routinely.
3. **Provenance.** `run.json` stores the commit and a dirty flag, not a binary hash or KiCad version
   (`:234-236`); the documented base line `base-1` and `valid-*` were taken from a dirty tree
   (`run.json: "dirty": true`); a board's `result.json` is reused if present (`:163-164`) and
   `run.json` overwritten on each invocation, so a resumed run can mix binaries.
4. **Referee failure counts as router failure.** `drc()` returns `None` when kicad-cli produced no
   report (`:72-77`), `score` is skipped (`:183-184`), and `report` classes the board as "router
   failed" (`:280`).
5. **Timeouts are not bounds** (§3.6), so the "120 s" number in the tables is nominal: the p90 wall
   time in `base-4` is 128 s and the maximum 421 s, with one `hung` kill at 660 s.
6. **Load.** Runs go `$RESERVED_CORES` boards at once with `--threads 1` and wall-clock budgets, so
   the result depends on how many neighbours a board had.
7. **Dangling copper and mask bridges are exempt** from "routed" (`:40, :259-261`), and
   `kicad_bench.py:32-34` exempts `isolated_copper` and `starved_thermal` too, so a change that
   leaves stubs, bridges or carves up planes reads as neutral.

## 3. Algorithmic assessment

### 3.1 The core approach

The router is: one conservative obstacle map per net class on a uniform grid (50 µm default,
`grid.rs`); A* on the CPU with an octile heuristic and a pocket pre-check (`search.rs`); PathFinder
negotiated congestion over all open connections with present and history prices, exact per-class
zones, via pricing, repasses and a rescue for walled-off connections (`negotiate.rs`); a finishing
pass one connection at a time; rip-up of the router's own copper; a "region plough" that rips and
renegotiates around a trapped path (`shove.rs`); a pre-fanout of fine-pitch parts on a 10 µm local grid
(`prefanout.rs`); coupled diff pairs (`pairs.rs`); then via reduction, pull-tight and cleanup.

**Is it a dead end?** No. For boards of the size in PCBench and on the two target boards it beats
FreeRouting on completion by KiCad's judgment, which is the metric that matters. The exact-check
discipline makes "0 new errors" cheap to keep. What the architecture cannot do without a change of
shape:

- **Scale.** Memory and time are proportional to board area ÷ cell² × layers (§3.6). Nothing picks
  the cell from the board; nothing windows the search except in the sub-routers.
- **Choose layers globally.** Each connection picks its layers by its own via price, in whatever order
  it comes; the result is the 2–5× via excess the project has been fighting with per-stage prices
  (`via_costs`, `lib.rs:987-997`: 500/600/320 normally, 200/80/80 with planes, both tuned by hand).
- **Treat fine pitch as the normal case.** The 50 µm global grid cannot resolve a 0.4 mm QFN's
  lanes, so pre-fanout runs a second router at 10 µm in windows with its own escape modes, orders,
  rings and hand-offs (1,825 lines), and the plough exists to recover what the global grid walls in.
- **Bound time.** Unreachable targets cost a whole-grid search each (§3.2).

The standard remedy in VLSI and in the better PCB routers is a **two-level router**: a coarse global
stage that assigns every connection a corridor and a layer under capacity constraints, then a
detailed stage that routes inside the corridor on the fine grid with a bounded window. The project's
own design doc proposes exactly this as milestone 6 ("Hybrid GPU global plus CPU detailed") and the
code already has the hook: `--regions` turns planner polygons into per-net `prefer`/`avoid`/`never`
costs on the fine grid (`grid/src/regions.rs`, `ultraroute/src/regions.rs`). A global router whose
output is a set of such regions per net is a one-to-two-week experiment that needs no change to the
detailed router.

### 3.2 Where the time goes

From `base-4` (1,182 boards, 120 s, one thread): median 12 s, p90 128 s, 166 boards at the limit,
of which 9 still clean; 257 failures, 157 of them time-limited and 99 open under the limit. The boards
at the limit have a median of 294 connections against 67 for the rest. So **time, not routability,
is the main failure mode on the corpus**, and the failures concentrate on the large boards.

Three slow boards, from their `base-4` logs (120 s timeout) and from verbose re-runs I made today at
`--timeout 60` on one thread (§A.4):

The common cause is that the expensive primitives have no work bound: `route_astar` expands until the
heap is empty when the target is unreachable (`search.rs:298-343`), the pocket check gives up at 1,024
nodes (`:231-281`), and `terminals` tries up to 16 candidate legs per anchor per layer, each an
insert-check-discard on the exact board (`route.rs:447, 490-495, 514-519`). On a 2,000-net board
with many walled-in pads these costs are paid thousands of times before any routing starts.

*Fixes, in order of payoff per effort:*

1. **Reachability labels per map** (days): connected components of the free cells of each class map
   (incrementally updated when copper is stamped, or recomputed per round), so `has_way`,
   `reachable_airlines`, `routable_open` and the A* pre-check are O(1) lookups and an unreachable
   target never starts a search. This alone removes the Teensy-style set-up blow-up and most of the
   "no path" exhaustion inside rounds.
2. **Expansion caps** on every A* (a function of the airline's length in cells) and a `Deadline`
   checked inside the search loop (hours).
3. **Reroute only colliding connections after round one** (a day). `run_pass` reroutes every
   connection every round (`negotiate.rs:693-721`); standard PathFinder practice reroutes nets that
   collide or whose cost dropped, cutting work per round by several times on boards where most
   routes settle early.
4. **Cheaper terminals** (days): compute legs once per pad per class and cache them across stages;
   `terminals()` is recomputed by negotiation, finishing, rip-up, the plough, the rescue and via
   reduction.

### 3.3 Negotiation specifics

The PathFinder implementation is thoughtful: per-class zones computed from exact pair geometry
(`all_zone_discs`, `negotiate.rs:1520-1551`), rim stamping to avoid re-marking discs
(`FastDisc`), via and hole-ring claims, a commit order that favours routes with fewer conflicts
(`commit_order`), repasses with a new seed, and a bounded rescue of walled-off connections. Things I
would change:

- **Zones store per-net cell sets as `HashMap<u32, HashMap<u32, u16>>`** (`:234-237`). The comment
  admits millions of entries. A flat per-net bitset over the round's nodes (or a run-length list
  sorted by node, since zones are generated sorted) would be several times smaller and faster.
  *Judgment; days.*
- **Present-price growth 1.6 per round with patience 4** (`:91-99`) and `SMALL` passes forced to 8
  rounds: on boards where negotiation gets 1–2 rounds before its budget (every large board), the
  history term never accumulates and the pass degenerates to greedy routing in seed order. A
  work-based budget (rounds) rather than seconds would at least make this visible.
- **Gauss-Seidel vs Jacobi** (§1.7): pick one. Jacobi parallelises; Gauss-Seidel converges in fewer
  rounds. The usual compromise is Jacobi with partial rerouting.
- **Directional costs only on two-layer boards** (`route.rs:169`, `negotiate.rs:619`). Preferred
  direction per signal layer (H/V alternating) is standard on 4+ layers and is the cheapest known
  way to cut vias and crossings in grid routers. *Judgment; a day.*
- **Via prices per stage** (`lib.rs:987-997`): negotiation 500, finishing 600, rip-up 320 "below its
  400 for ripping copper", and 200/80/80 with planes. These interact with `--cell` (the price is in
  cells, `via_cost_mm`) and with the history term. One price in millimetres, applied everywhere, with
  the layer decision moved to a global stage, is the clean version.

### 3.4 The GPU

Diagnosis is in §1.4: dense Bellman-Ford per field against a sparse CPU A*. Options:

1. **Park it** (hours): remove `GpuSweepSolver`, keep `GpuSolver` behind the feature with a note that
   it is 10× slower on real boards, and stop advertising GPU routing until there is a GPU-shaped
   problem. This is what I would do this month.
2. **Use it where many independent searches of similar size happen on a coarse grid**: the global
   stage of §3.1. A GCell grid of 0.5–1 mm has a few thousand to a hundred thousand nodes; batching
   hundreds of nets per dispatch is where GPU global routers (CUGR, FastGR, InstantGR) get their
   speed. Even there, a CPU implementation first is the right order: a 100k-node global stage is
   milliseconds on one core.
3. **Frontier-based kernels** (weeks): if the GPU must do detailed routing, the kernel needs a compact
   frontier (work queue) and multi-source batching so a dispatch touches O(frontier) nodes, not O(all
   nodes), plus GAMER-style sweeps for the straight stretches. `sweep.wgsl` was a start down this road
   and was abandoned. I would not spend the next month here: the CPU A* with the fixes in §3.2 will
   be faster than any GPU field solver on these boards.

WebGPU in the browser adds constraints the current solver ignores: a 128 MiB storage-binding limit
by default (the earring's batch of 16 fields is ~730 MB of buffers), no `pollster::block_on`, and the
`required_limits: adapter.limits()` request (`gpu.rs:65`) fails on adapters below the native card's
limits. The browser build's worker pool is the right design for WASM; it should be described as such.
The GPU audit's ranking of what to try, if the GPU is kept, agrees with mine: window each field to a
box around its ends (the host already computes pockets and A* already has a target box; 2–4 days,
5–50× on short connections), and measure a coarser negotiation cell with fine finishing passes
(0 days to measure); only if those fail is a frontier-compacted bucketed kernel or a productionised
sweep kernel (1–2 weeks each) worth writing, and even then it is likely to land at or below CPU A*.

### 3.6 Resource limiting and graceful degradation

The brief asks that the router never peg or crash the host. Today:

- **CPU.** `--threads` defaults to half the cores and is honoured by negotiation only; nothing sets
  OS priority (`nice`) or yields. Acceptable, but the design doc's "run at low priority by default" is
  not implemented; the user's `reserve` wrapper does the job outside.
- **Time.** `--timeout` is split into fractions (§1.3) with gaps: pre-fanout, plane joining, cleanup,
  length matching and the diff-pair inner loops have no budget; the A* has no expansion bound; the
  pre-round set-up of negotiation is uncounted. Measured: 166 of 1,182 boards over the limit, with
  overruns of 3–5× on three boards and a kill at 660 s on one. Each stage reads its own clock from
  its own start, so there is no notion of "the run must end at T". *Definitely wrong; high; days for a
  `Deadline` threaded through every loop, weeks for every stage to degrade gracefully.*
- **Memory.** No cap, no coarsening, no estimate before allocation. Grid memory is
  `layers × nx × ny × (4 B owner + 1 B blocked + 4 B penalty + 4 B region) per class` plus
  `20 B per node per thread` for A* buffers plus negotiation's zones; the lab's peak RSS over 1,751
  runs is median 344 MB, p90 582 MB, maximum 5.1 GB (easy2350 at `--cell 0.010`). The only guard
  is the `systemd-run MemoryMax=8G` wrapper in the harness (`pcbench.py:41`), which is outside the
  router. A router that knows its own node count can choose a cell, refuse a run, or window, before
  allocating. *Definitely wrong for the stated goal; high; a day for an estimate and a refusal, more
  for adaptive cells.*
- **GPU.** Submissions are batched to 32 dispatches with a read-back between (`gpu.rs:9, 452-469`),
  which does keep the desktop responsive; but neither the deadline nor `cancel` is consulted inside a
  batch (§1.4).
- **The studio** (per the GPU audit, which read `studio/server/src/main.rs`): runs one router at a
  time under `nice 15`, kills the child's parent-death, sends `stop` 20 s past the limit and SIGKILLs
  8 s later, but injects no `--threads` and no memory cap, so a studio run takes half the cores and
  whatever memory the board needs; live frames go through a bounded 1,024-line channel whose sender
  blocks, so a slow WebSocket client stalls the router while its wall-clock budget drains
  (`lib.rs:685-689`).
- **Degradation.** When time runs out, the board so far is written, which is right. But there is no
  "good enough" stopping (the design doc's "stop when completion and DRC targets are met"), no
  checkpointing, and no progress report that a caller could use to decide; the studio gets frames,
  the CLI gets `eprintln!`.

## 4. Development approach

### 4.1 Is it converging?

The honest answer is: it converged on the two target boards and on PCBench's median board, and it is
now accumulating special cases faster than it accumulates structure.

Evidence for convergence: the PCBench clean rate went 43.8% → 75.3% → 78.3% across three commits
in five days, mostly by closing rule gaps the referee exposed (`docs/pcbench.md`), and both target
boards route to 0/0 on several seeds. Judging by KiCad after a refill, against bare boards, with
"new error types" diffed per board, is the right referee and the project got there early.

Evidence for fragility:

- Four of the eight merges are labelled "Gemini agent, unaudited" in the commit log; the audit
  that followed found one of them changed the default seed's result through a side effect
  (`docs/focus-trapped-escapes.md:264-269`) and another had changed `shove.rs` in three worktrees
  at once.
- The flag count (77), the plough variants (6), the written-down recipes (10), the cleanup
  heuristics keyed to named boards, the plane-net special cases in four modules, and the per-stage
  via prices are all shaped like "the last board we looked at".
- The lab log for the earring shows the loop: a stage is added, scores a win on one seed, is merged,
  then the next sweep over seeds finds the mean unchanged (`focus-trapped-escapes.md:117-121,
  158-159, 180-184`). The reason is §1.7: single runs are within noise, and nobody could tell.
- Nothing prevents the next agent from re-adding what the last removed: no CI, no gate, no
  structured stats to compare.

What is working in the process and should be kept: the referee, the lab as the record, worktrees per
experiment, audits before merge (when they happen), and the habit of writing down what was tried.

### 4.2 Instrumentation and tooling I would add

1. **Structured run stats.** One JSON record per run with per-stage wall time, work (A* calls and
   expansions, connectivity recomputes, `check_item` calls, obstacle-map builds), open count before
   and after, copper laid and ripped, peak RSS, grid dimensions and node count, thread count, seed,
   budget mode, binary hash. Written by the router (`--stats FILE`), not regexed from `stderr` by
   `lab.py`. Every finding in §3.2 took me log archaeology to establish; it should be one column.
2. **A `Deadline` with a trace**: which stage was running when the clock ran out, how far over, and
   what it was doing (the connection and primitive). Today the only evidence of a 313 s diff-pair
   stage is the cumulative time on the next line.
3. **A per-connection failure record** that survives to the output: `Stats.failures` already has
   `(from, to, reason)`; add the stage, the pocket size, the cheapest blocking nets, and write it to
   the stats file and into the `.kicad_pcb` as a comment or a side file. `--blame` does this on
   demand; it should be free.
4. **Occupancy and congestion maps as data**, not only as studio frames: a per-layer GCell histogram
   of claimed cells at the end of negotiation, exported to the lab, so "where is the board full" is a
   picture before anyone adds a stage.
5. **The films as a library feature, not a 3,860-line example.** `feature_film.rs` re-implements the
   stage drivers to record frames; a `watch` hook on the real pipeline (which already exists for the
   studio) would record the same films from the real code and stop the two from diverging.
6. **A `compare` command and a noise floor** (§2.4), and a nightly run of a fixed 200-board subset
   with three seeds, kept as the baseline.

### 4.3 What I would do with the next month

In order, and I would not start a later item before the earlier one is merged:

1. **Week 1: make runs measurable.** CI with the test suite. `Deadline` threaded through every stage
   and search loop; budgets in work with a hard wall-clock stop; one negotiation mode; the via pass
   and pre-fanout under the budget; reachability labels and expansion caps. `pcbench.py compare`
   with binary hashes and a measured noise floor on a 200-board subset × 3 seeds. The three slow
   boards as a hard-timeout test. Expected result: no board over its timeout, identical output for
   identical inputs, and a benchmark that can see a 2% change.
2. **Week 2: make the good router the default and delete the rest.** The PCBench recipe becomes the
   no-flag behaviour. Remove `Linear`/`Warp`/`Gentle`/`Dipole` ploughs, `--escape`, `--clear-lanes`,
   `--push`, `--chase`, `--topo*`, `--first*`, `--restart`, the legacy modes, `GpuSweepSolver`,
   `pocket_bbox`; move the topo crate and `feature_film.rs` to an `experiments/` workspace that CI
   builds but the pipeline does not link. Refactor `run_with_solver` into stages over one `Laid`
   ledger. Re-run the benchmark to prove nothing moved beyond noise.
3. **Weeks 3–4: a global stage.** Coarse grid (1 mm GCells, one per layer), capacity per GCell edge
   from the obstacle maps, PathFinder over all connections at that scale (seconds), layer assignment
   by the same negotiation, output as per-net `prefer`/`avoid` regions into the existing `--regions`
   path, and a `via_cost` that no longer differs per stage. Measure vias, time and completion on the
   200-board subset. If it pays, make the detailed router window its searches to the corridor
   (bounded memory follows).

Things I would leave alone until then: the GPU, the topological router, placement (push, nudge,
diffusion), the browser pool, and any new rescue stage. Every one of them is either unmeasurable
today or solves a problem the global stage would remove.
