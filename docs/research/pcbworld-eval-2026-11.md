# Scoring `ultraroute` Under PCBWorld's Dataset, Evaluator, and Metrics

## Executive Summary

We evaluated `ultraroute` at `main` (`aae1126`, release binary `sha256: 221e2c8c1efb...` with `kicad-text` `sha256: a7a1bb1797cc...`) on **PCBWorld's own D3 board files**, using **PCBWorld's own C++/Python evaluator** (`eval.metrics.evaluate_one` backed by `PCBWorld-Engine` `kicad_rl_router.so` on KiCad `9.0.8`) and **PCBWorld's exact metric definitions** from `arXiv:2607.05915v4` ([`LGAI-Research/PCBWorld`](https://github.com/LGAI-Research/PCBWorld) `v1.1.1`, commit `1989a93`). No PCBWorld, KiCad, or Freerouting code or data is copied, linked, or vendored into this repository; [`tools/pcbworld/pcbworld_bench.py`](../../tools/pcbworld/pcbworld_bench.py) is MIT-licensed standard-library Python that invokes an external PCBWorld checkout over board files on disk.

## 2. Evaluator Verification: Reference & Freerouting 2.1.0

### 2.1 Potential Formula Reconciliation (`Table 3` vs. `PAPER_SCORING_FLAGS`)
Before trusting scores, we checked `Reference` (`processed_v9_guide_v3.kicad_pcb`) against Paper Table 3 & Table 21 (`D3-A Pot. = 23.16`, `D3-B Pot. = 63.96`):
- PCBWorld's `experiments/kdd/configs/paper_train_flags.sh` defines `PAPER_SCORING_FLAGS="--reward-config drc_dense_promoted"`, whose YAML sets `wirelength_penalty: 0.0, via_penalty: 0.0` (yielding `23.62` on D3-A Reference and `65.77` on D3-B Reference), while `run_rule_based_routers.py` defaults to `--reward-config pcbworld_reward` (a linear pad-group reward, completely different scale).
- Paper Appendix G (lines 1124, 1149, 1159) and Appendix K.2 (Table 15) state the exact potential function used in Table 3, Table 21, and Table 22:
  $$\Phi(s) = -\bigl(f_{\mathrm{drv}}(s) + 0.002\,\ell(s) + 0.1\,n_{\mathrm{via}}(s)\bigr), \qquad \Delta\Phi(s) = \Phi(s) - \Phi(s_0),$$
  where $f_{\mathrm{drv}}(s)$ is `drc_dense_promoted` ($s_{\mathrm{agg}}=3, s_{\mathrm{pn}}=1, o=2$) and $s_0$ is the bare board ($\ell(s_0)=0, n_{\mathrm{via}}(s_0)=0$). Applying $(\lambda_w, \lambda_v) = (0.002, 0.1)$ to `drc_dense_promoted` reproduces Paper Table 3 & Table 21's Reference rows **to two decimal places**:
  - **D3-A Reference (99 boards):** `CP = 1.0000` (paper `1.00`), `Pot. = 23.1629` (paper `23.16`), `Rout. = 1.0000` (paper `1.00`), `DRV = 0.00` (paper `0.00`), `WL = 170.19 mm` (paper `170.2`), `Via = 1.1818` (paper `1.18`).
  - **D3-B Reference (10 boards):** `CP = 1.0000` (paper `1.00`), `Pot. = 63.9551` (paper `63.96`), `Rout. = 1.0000` (paper `1.00`), `DRV = 0.00` (paper `0.00`), `WL = 570.31 mm` (paper `570.3`), `Via = 6.7000` (paper `6.70`).
  - Both `potential_gain_table3` ($\lambda_w=0.002, \lambda_v=0.1$) and `potential_gain_true_phi0` ($\lambda_w=\lambda_v=0$) are recorded in [`docs/research/pcbworld_eval.json`](pcbworld_eval.json).

### 2.2 Reproducing Freerouting 2.1.0 on D3-A and D3-B (and Explaining the `0.80 -> 0.9191` Gap)
We ran PCBWorld's `methods/baselines/rule_based/run_rule_based_routers.py --baseline freerouting --max-passes 10 --timeout 1800 --reward-config drc_dense_promoted` across **5 rollouts** (`rollout_0..4`) on **D3-A** (495 runs) and **D3-B** (50 runs), stored under `~/ab/pcbworld-runs/freerouting/rollout_{0..4}/`:
- **Timeouts:** **0 timeouts** across all 545 runs (every run finished well below `DEFAULT_TIMEOUTS["freerouting"] = 1800 s`; the slowest single board was `0024_memsarray_mems_modules` at `671.64 s` in `rollout_0`). Note: `rollout_0` and `rollout_2` ran with `--workers 4` on 5 booked cores without `-XX:ActiveProcessorCount=1`, causing JVM thread contention (`22.78 s` mean on D3-A); adding `-XX:ActiveProcessorCount=1` with `--workers 3` (`rollout_1, 3, 4`) gave `8.82–9.76 s` per board (close to the paper's `7.09 s`).
- **Scores under `PCBWorld v1.1.1` (`1989a93`):**
  - **D3-A (`n = 99`):** `@5`: `CP = 91/99 (0.9191)`, `Pot. = 22.95`, `Rout. = 0.9947`, `DRV = 0.15`, `WL = 153.14 mm`, `Via = 0.87`, `Time = 12.84 s` (`9.21 s` mean over unthrottled `rollout_1,3,4`). `@1` (`mean ± std` over 5 rollouts): `CP = 0.8424 ± 0.0233` (`81, 81, 85, 84, 86` clean), `Pot. = 22.22 ± 0.10`, `Rout. = 0.9804 ± 0.0031`, `DRV = 0.36 ± 0.04`, `WL = 153.02 ± 0.70 mm`, `Via = 0.90 ± 0.05`.
  - **D3-B (`n = 10`):** `@5`: `CP = 9/10 (0.9000)`, `Pot. = 64.51`, `Rout. = 1.0000`, `DRV = 0.20`, `WL = 528.69 mm`, `Via = 2.90`, `Time = 18.03 s` (`8.50 s` over `rollout_1,3,4`). `@1`: `CP = 0.7800 ± 0.1304` (`6, 8, 7, 9, 9` clean), `Pot. = 62.50 ± 0.86`, `Rout. = 0.9918 ± 0.0050`.
- **Why `v1.1.1` (`0.9191` CP@5) is ~12 points higher than Paper Table 3 (`0.80` CP@5):**
  Inspecting `git diff ed41174..1989a93 -- methods/baselines/rule_based/` between `v1.0.0` (initial paper release) and `v1.1.0`/`v1.1.1` proved two post-paper bug fixes in PCBWorld's Freerouting pipeline:
  1. **Unmapped Specctra copper-layer aliases in `v1.0.0` `ses_to_kicadpcb.py`:** Eight D3-A boards declare custom copper layer names in KiCad (`Top`/`Bottom` on `0017`, `0021`, `0048`, `0049`, `0050`, `0051`; `1_top`/`4_bot` on `0067`; `Front` on `0100`). Specctra `.dsn`/`.ses` files emit those aliases verbatim. Running `ed41174:methods/baselines/rule_based/_converters/ses_to_kicadpcb.py` + `pcbnew.LoadBoard` on our 495 `.ses` files confirmed that **all 8 boards fail `pcbnew.LoadBoard` (`NoneType`)** under `v1.0.0` and get folded by `FOLD_ZERO_ON_ALLFAIL` to `CP = 0.0, Rout. = 0.0`. Folding just those 8 boards on our 5 rollouts immediately changes D3-A to:
     - **`Rout.@1 = 0.9009 ± 0.0037`** (Paper Table 22: **`0.90 ± 0.00`**),
     - **`Rout.@5 = 0.9140`** (Paper Table 3 & 21: **`0.91 ± 0.00`**),
     - **`WL@1 = 156.4 ± 0.8 mm`** (Paper Table 22: **`156.6 ± 1.0`**), **`Via@1 = 0.85 ± 0.05`** (Paper Table 22: **`0.86 ± 0.05`**),
     - **`CP@5 = 84/99 (0.8484)`** and **`CP@1 = 0.7859 ± 0.0280`** (`74/99 = 0.7474` on `rollout_0,1` vs Paper Table 22's **`0.75 ± 0.01`**).
  2. **Pre-`make_dsn_orp_v3.py` `.dsn` rule export mismatches:** As PCBWorld's own `methods/baselines/rule_based/README.md` (lines 64, 180) and `eval/_scripts/pcbench_fair95.txt` (`# Compat: FR=0004,0024,0035,0077`) document, the paper's archived logs ran on stock `ExportSpecctraDSN` outputs before `make_dsn_orp_v3.py` patched exact `.kicad_pro` netclass clearances, widths, and decimal via sizes into `.dsn`, inflating paper `DRV@5` (`0.86` vs `0.15`) and accounting for the remaining ~4 boards between `0.85` and `0.80` on D3-A (and `0.90` vs `0.78` on D3-B).

### 5.2 Disagreements Between PCBWorld's Evaluator and `pcbench-judge` on the Same Output
We ran `pcbench-judge` (`kicad-cli` 9.0.8 + `pcbnew.ZONE_FILLER` + bare-board error subtraction) on the **exact same 677 `seed 1` `(out.kicad_pcb, out.kicad_pro)` pairs** scored by PCBWorld (`docs/research/pcbworld_eval.json` -> `cross_judge_seed1`), plus `s3:0052_breakout-boards_50-to-100`:
- **Empirical result on `ultraroute` outputs:** **0 disagreements across all 677 `seed 1` boards** (`D3-A`: `98` both clean / `1` both fail; `D3-B`: `10/0`; `D3-C`: `10/0`; `medium.train`: `283/3`; `hard.train`: `270/22`), and **agreement on `s3:0052`** (both flag the single clearance error between `PTH pad 5 [/5] of P2` and `Track [/6] on F.Cu`).
- **Why they agree 100% here — and where they differ architecturally:**
  1. Both read PCBWorld's `processed_v9_guide_v3.kicad_pro` (which already sets `solder_mask_bridge`, `copper_edge_clearance`, `hole_clearance`, and `annular_width` to `ignore`), and all 677 D3 boards contain `0` copper zones, `0` keepout zones, and `0` `.kicad_dru` files.
  2. Architecturally, `kicad_rl_router.so` (`engine/src/rl_router.cpp`) compiles only **9 DRC providers** (omitting `edge_clearance`, `solder_mask`, `disallow` keepouts, `zone_connections`, and `drc_rule_condition`) and **does not subtract pre-existing bare-board errors**, whereas `pcbench-judge` runs full `kicad-cli` DRC after zone refill and subtracts bare-board errors on non-routed items. On boards with keepout zones, copper pours, `.kicad_dru` rules, or un-ignored `.kicad_pro` mask/edge/hole checks, `pcbench-judge` is strictly stricter on routed copper while tolerating pre-existing bare-pad defects.

## 6. Benchmark & Evaluator Bugs Found in PCBWorld

Every item below was verified directly in PCBWorld's source/bytecode and raw evaluation files:

1. **Freerouting 2.1.0 `-mp 10` Is Ignored (`stop_pass_no = 999`):**
   Disassembling `external/freerouting/freerouting-2.1.0.jar` (`javap -c app.freerouting.settings.GlobalSettings`, `RouterSettings`, `autoroute.BatchAutorouter`) shows `-mp 10` sets `RouterSettings.maxPasses = 10`, a field **never read by `BatchAutorouter`**. Instead, `BatchAutorouter` loops while `pass_no <= settings.get_stop_pass_no()`, initialized at `RouterSettings.<init>` bytecode offset `102` (` sipush 999`) to **`999`**. In our `rollout_0` logs (`~/ab/pcbworld-runs/freerouting/rollout_0/.../raw/*.routing.log`), **14/99 D3-A boards** and **4/10 D3-B boards** ran >10 passes, with **8 D3-A boards hitting pass `#999`** (`0024`, `0034`, `0052`, `0063`, `0075`, `0086`, `0087`, `0099`).

   When `evaluate_one()` scores a routed board file offline, it estimates $\Phi(s_0)$ by calling `strip_NonPadStubs`, which retains track segments touching pads. Any violation or wirelength on pad-touching segments contaminates `initial_potential`, under-reporting `potential_gain` unless bare-board $\Phi(s_{b,0})$ is evaluated separately on the unrouted board (which `experiments/kdd/rl_eval/common.py` had to work around via `_bare_board_phi0`, while `eval.aggregation` does not).

## 7. What We Did Not Do

- **No Synthetic Suites (D1, D2):** Per task scope, we evaluated D3 (PCBench-derived real boards: D3-A, D3-B, D3-C, `medium.train`, `hard.train`) and did not generate or score synthetic D1/D2 boards.

## For the project memory

- **`Board::mask_openings` ignores `.kicad_pro` `solder_mask_bridge: "ignore"`:** On `0068_AVR-ISP_pogo-plug_1.27mm` (our sole failure across all 119 D3-A/B/C test boards), footprint `P2` has a layer typo putting `F.Mask` on three `B.Cu` pads co-located with `F.Cu` pads. `ultraroute` blocks `F.Cu` escape even when `.kicad_pro` sets `"solder_mask_bridge": "ignore"`. Honoring `.kicad_pro` severity (or ignoring cross-side mask openings on pads with no copper on that side) would likely make D3-A `99/99` (`100%`).
